1: # ROS 인터페이스 색인
2: 
3: 각 노드의 발행, 구독, 서비스 제공/호출, 액션 제공/호출을 찾는 색인이다. 상세 표는 코드 옆 `docs/interfaces.md`가 관리하고, 동작과 안전 규칙은 [INTEGRATION](INTEGRATION.md)의 계약 reference를 따른다.
4: 
5: 표는 현재 소스와 launch의 기본 이름을 기록한다. 실행별 namespace, node name, parameter와 remap에 따라 실제 graph는 달라진다. 조건부 endpoint, 외부 server, 미구현 타입을 구분하며 모든 노드가 동시에 실행되는 것으로 해석하지 않는다.
6: 
7: ## 표 읽기
8: 
9: | 표기 | 뜻 |
10: |---|---|
11: | 토픽 발행 / 구독 | 해당 노드에서 나가는 데이터 / 들어오는 데이터 |
12: | 서비스 제공 / 호출 | Server / client |
13: | 액션 제공 / 호출 | Action server / client |
14: | R10, R20, R1 | Reliable, volatile, keep-last depth 10 / 20 / 1 |
15: | B1 | Best-effort, volatile, keep-last depth 1 |
16: | Sensor | Humble `qos_profile_sensor_data`: best-effort, volatile, keep-last depth 5 |
17: | R/T1, R/T2048 | Reliable, transient-local, keep-last depth 1 / 2048 |
18: | Service 기본값 | Humble service QoS: reliable, volatile, keep-last depth 10 |
19: | Action 기본값 | rclpy 기본 request/result/cancel service와 feedback/status QoS. Status는 reliable, transient-local, depth 1 |
20: | TF 기본 QoS | tf2_ros broadcaster/listener 기본값. 응용 코드가 별도 QoS를 지정하지 않음 |
21: | 상대 이름 / `/절대 이름` / `~/private` | Node namespace 적용 / root 이름 / node namespace와 node name 적용 |
22: | 주기 | 소스의 기본 timer 또는 callback 조건. 실제 수신 빈도와 동일하지 않을 수 있음 |
23: 
24: ## 종류별 통합 목록
25: 
26: [Topic](#topic-목록), [Action](#action-목록), [Service](#service-목록)에서 이름으로 찾는다. 노드 링크는 패키지의 상세 표로 연결하며, 아직 표에 없는 runtime endpoint는 구현 소스로 연결한다. QoS와 호출 조건은 연결된 문서와 소스를 따른다.
27: 
28: 아래 이름은 **root namespace에서 기본 이름을 해석한 값**이다. 상대 이름을 절대 이름으로 고정하는 설정이 아니며, namespace, remap과 parameter override가 있으면 달라진다. `cleany_dev_monitor`의 `runtime_namespace`는 기본 빈 값으로 표시했다. `<...>`는 실행 시 결정되는 이름 패턴이다.
29: 
30: 발행/제공 목록의 여러 노드는 실행 구성에 따른 대안이거나 서로 다른 데이터를 같은 토픽으로 보내는 노드다. 동시에 실행한다는 뜻은 아니다. `mock_*`, Gazebo, MuJoCo와 `sorting_cameras`는 mock 또는 시뮬레이션 경로이며, 외부 Nav2, MoveIt과 controller는 별도 실행이 필요하다. `—`는 이 색인에서 상대 노드를 지정하지 않은 항목이며, endpoint의 부재나 미구현을 뜻하지 않는다. `SortingObserver`는 MuJoCo host 노드에 붙는 plugin이며 독립 노드 이름이 아니다. Monitor의 동적 구독은 discovery와 사용자 선택에 따라 생성된다.
31: 
32: ROS 자동 인터페이스는 [별도 표](#ros가-자동-생성하는-인터페이스)에 둔다. 응용 코드가 직접 호출하거나 관찰하는 action cancel/status와 카메라 parameter 서비스는 통합 목록에도 표시한다. 외부 패키지 전체 API와 실행 중 동적으로 발견되는 모든 이름을 열거하지는 않는다.

316: ## ROS가 자동 생성하는 인터페이스
317: 
318: Parameter 서비스와 이벤트, rosout, sim clock 구독, action 내부 전송은 응용 표에서 반복하지 않는다. 아래 패턴이 노드 옵션과 실행 상태에 따라 추가된다.
319: 
320: | 항목 | 기본 패턴 / 타입 |
321: |---|---|
322: | Parameter 서비스 | `<node>/{describe_parameters,get_parameter_types,get_parameters,list_parameters,set_parameters,set_parameters_atomically}`; `rcl_interfaces/srv/*` |
323: | Parameter 변경 이벤트 | `/parameter_events`; `rcl_interfaces/msg/ParameterEvent` |
324: | 로그 | `/rosout`; `rcl_interfaces/msg/Log`, rosout 활성화 시 |
325: | Simulation clock | `/clock`; `rosgraph_msgs/msg/Clock`, ROS time source 연결 시; `use_sim_time`으로 시간 적용 선택 |
326: | Action 요청 / 결과 / 취소 | `<action>/_action/{send_goal,get_result,cancel_goal}` 서비스 |
327: | Action feedback / status | `<action>/_action/{feedback,status}` 토픽 |
328: 
329: 명시적으로 만든 cancel client와 status subscription은 호출 노드의 표에도 표시한다. ESP32 rclc 노드는 표에 적힌 wheel interface만 초기화하며 rclpy의 자동 parameter 서비스가 동일하게 생긴다고 가정하지 않는다.

331: ## 실행 중 확인
332: 
333: 실행한 구성과 같은 DDS domain, 같은 overlay의 터미널에서 확인한다.
334: 
335: ```bash
336: ros2 node list
337: ros2 node info /mission_runtime
338: ros2 topic list -t
339: ros2 topic info /cmd_vel --verbose
340: ros2 service list -t
341: ros2 action list -t
342: ros2 action info /grasp/select_reachable
343: ```
344: 
345: 실행 그래프는 해당 실행 시점의 실제 연결 상태를 나타냅니다. 조건부 노드가 실행되지 않았다고 해서 소스 코드의 전체 인터페이스 정의가 누락된 것은 아닙니다. 코드 및 인터페이스를 변경할 때는 관련 패키지의 인터페이스 표와 이 색인 문서를 함께 갱신합니다.
